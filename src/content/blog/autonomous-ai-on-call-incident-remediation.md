## 1. Executive Summary and High-Level Architecture

### 1.1 Problem statement

The operations team handles more than ten urgent alerts per day. A substantial portion of engineer time is spent acknowledging alerts, assembling context across observability systems, locating a runbook, and executing a familiar recovery procedure. The repetition creates alert fatigue, increases handoff cost, and makes mean time to recovery dependent on who is on call.

Historical incident analysis indicates that approximately 40% of alerts map to a known failure signature, an approved runbook, or a standard configuration fault. These cases are candidates for automated diagnosis and, where the risk model permits, automated remediation. The remaining incidents still benefit from evidence collection, hypothesis ranking, and a concise handoff to a human incident commander.

This RFC proposes an **Autonomous AI On-Call and Incident Remediation System** that intercepts alerts, selects either a deterministic quick path or a context-aware retrieval path, produces an evidence-backed root-cause analysis, and executes only policy-approved actions. The system is not an unconstrained chatbot with production credentials. It is a bounded workflow engine in which an LLM may propose decisions while deterministic policy, authorization, and verification layers control effects.

### 1.2 Goals and service-level objectives

| Objective | Initial target | Measurement window |
|---|---:|---:|
| Automatically close eligible incidents without human intervention | ≥ 40% of onboarded, policy-eligible alerts | Rolling 30 days |
| P95 time from accepted alert to initial diagnosis | < 30 seconds | Rolling 7 days |
| P95 quick-path routing and plan generation | < 1 second, excluding external tool latency | Rolling 7 days |
| Correct escalation when confidence or evidence is insufficient | ≥ 99.9% | Rolling 30 days |
| Unsafe autonomous destructive actions | 0 | Continuous |
| Reduction in MTTR for eligible alert classes | ≥ 50% from pre-launch baseline | Quarterly |
| Evidence citation coverage for diagnostic claims | 100% | Per report |
| Availability of alert ingestion and orchestration | 99.95% | Monthly |

A successful diagnosis is not merely an answer accepted by the model. It requires a supported cause, a policy-compliant response, post-action verification, and either explicit operator acceptance or an observable return to healthy service-level indicators.

### 1.3 Non-goals

The first release will not:

- autonomously execute arbitrary shell commands generated by a model;
- remediate unknown incidents with high blast radius;
- replace the incident commander during a major incident;
- train directly on raw production logs or private chat transcripts;
- treat model confidence as authorization;
- suppress an alert without a durable audit record and verification result.

The design consists of four logical layers:

1. **Trigger Layer:** authenticates alert sources, normalizes provider-specific payloads, deduplicates alert storms, groups correlated symptoms, and persists the canonical incident before acknowledging delivery.
2. **Execution Engine:** runs a durable state machine. It applies routing policy, invokes bounded agents, enforces tool and token budgets, requests approvals, and resumes safely after worker failure.
3. **Data Pipeline:** provides time-bounded telemetry, versioned runbooks, service topology, ownership, deploy history, and prior incident evidence. Retrieval indexes are derived data and can be rebuilt from authoritative sources.
4. **Feedback Loop:** captures outcomes, curates training and evaluation datasets, updates retrieval indexes, and promotes model or prompt changes only after offline and shadow evaluation.

### 1.5 Availability and state management

Alert acceptance and model inference have different reliability requirements and must not share a synchronous failure domain. The Trigger Layer writes every validated event to an append-only incident ledger and a replicated queue before returning success. Consumers use an idempotency key derived from `(source, source_event_id, fingerprint)`; repeated delivery updates the same incident rather than starting another remediation.

The Execution Engine stores every transition in a durable workflow system such as Temporal. Agent output, tool input, policy decisions, approvals, and verification results are immutable events. A worker can therefore retry or resume without repeating a destructive effect. Action tools require an `action_id` idempotency token and implement compare-and-set semantics where available.

Model providers, vector stores, and individual observability backends are protected by circuit breakers. If the RAG path is unavailable, the system degrades to deterministic evidence collection and human escalation. It must never degrade from “approval required” to “autonomous.”

## 2. Dual-Engine Architecture: Dynamic RAG vs. Direct Prompt Routing

### 2.1 Why two engines

A single retrieval-heavy agent is inefficient for known, fixed-shape alerts and unsafe for ambiguous incidents. Conversely, a static prompt cannot reason over a changing service graph or distinguish a deploy regression from downstream saturation. The Engine Router separates these workloads while preserving a common report schema, policy layer, and audit trail.

| Property | Direct Prompt quick path | Dynamic RAG path |
|---|---|---|
| Typical alerts | Disk full, certificate expiry, known consumer lag | 5xx spike, latency regression, cascading failure |
| Preconditions | Stable fingerprint, approved runbook version, complete parameters | Valid alert with resolvable service identity |
| Context | Alert fields and allowlisted live checks | Telemetry, SOPs, topology, deploys, prior incidents |
| Planning | Constrained template or structured model call | Multi-stage retrieval and hypothesis ranking |
| Target latency | < 1 second before tool execution | P95 diagnosis < 30 seconds |
| Variability | Very low | Bounded but context-dependent |
| Default action posture | Pre-authorized low-risk action only | Read-only diagnosis; approval for effects |
| Failure behavior | Escalate to RAG or human | Summarize evidence and escalate |

### 2.2 Static / quick-path mode

Quick-path eligibility is declared in a versioned **Alert Automation Registry**, not inferred solely by an LLM. Each entry contains:

- an exact or bounded fingerprint matcher;
- required alert fields and freshness constraints;
- an owner-approved runbook version;
- allowlisted read and action tools;
- preconditions, postconditions, and rollback behavior;
- severity and environment restrictions;
- maximum blast radius and concurrency;
- expiration date and approving service owner.

For example, a certificate-expiry alert may query the certificate inventory, verify the affected endpoint and remaining lifetime, invoke the approved renewal workflow, and verify the served certificate chain. A disk-full alert may identify a known disposable cache volume and execute a signed cleanup operation. It may not generate and run a novel deletion command.

“Deterministic prompt” does not imply that probabilistic generation becomes mathematically deterministic. Where possible, the quick path uses templates and ordinary code. If semantic normalization is necessary, the model runs with a fixed version, temperature zero, constrained decoding, and a strict JSON schema. The policy engine validates the result and rejects extra fields or unregistered tool calls. This approach can keep routing below one second while making the executable plan reproducible.

Quick-path routing requires all of the following:

```text
registry_match
AND fingerprint_confidence >= 0.98
AND required_fields_complete
AND runbook_status == APPROVED
AND alert_age <= registry.max_alert_age
AND environment IN registry.allowed_environments
AND current_blast_radius <= registry.max_blast_radius
AND no_change_freeze_violation
```

A failed predicate sends the incident to RAG mode or human escalation; it does not lower the threshold.

### 2.3 Dynamic / context-aware RAG mode

The RAG path performs **federated, time-aware, and topological retrieval**. It does not concatenate arbitrary search results into one prompt.

1. **Entity resolution:** map labels, namespace, cluster, endpoint, and ownership metadata to canonical service IDs.
2. **Temporal retrieval:** query metrics, logs, traces, and deploy events for a bounded window around the alert. Compare against an equivalent healthy baseline and account for seasonality.
3. **Topological retrieval:** traverse the Kubernetes and CMDB service graph from the affected service. Rank upstream and downstream nodes by edge type, error propagation, and temporal correlation rather than graph distance alone.
4. **Document retrieval:** fetch only active, access-authorized SOP sections and prior incident summaries. Apply hybrid BM25 and embedding search, then cross-encoder reranking.
5. **Change correlation:** retrieve Git commits, configuration changes, feature-flag updates, and deployments associated with candidate services. Bind every change to time, author, artifact digest, and rollback capability.
6. **Context assembly:** deduplicate evidence, enforce per-source quotas, preserve timestamps and provenance, and fit the result into a fixed context budget.

A useful retrieval score is:

$$
S(e) = w_s S_{semantic} + w_k S_{keyword} + w_t S_{temporal} + w_g S_{topology} + w_a S_{authority} - w_d S_{duplication}
$$

Weights are calibrated on resolved incidents. Authority and freshness must be explicit features: a current owner-approved SOP should outrank a semantically similar but retired incident note.

Each evidence item receives an immutable citation ID such as `metric:prometheus:query_hash:time_range`, `log:loki:query_hash:line_range`, or `git:repository:commit_sha`. The model sees compact evidence objects, not backend credentials or unrestricted raw streams.

### 2.4 Router precedence and fallback

Routing order is deterministic:

1. validate schema and authorization context;
2. check suppression, maintenance, and duplicate policy;
3. evaluate the automation registry;
4. choose quick path only when every eligibility predicate passes;
5. otherwise choose RAG when dependencies and budget are available;
6. otherwise collect minimum evidence and escalate.

The router records the matched rule, feature values, registry version, and reason codes. During rollout, a shadow router computes its decision without controlling execution; disagreements become evaluation examples.

## 3. Agentic Workflow and Autonomous Tool Execution

### 3.1 Durable multi-agent state machine

The word “agent” refers to a bounded role with a typed input and output, not an independent process free to invent goals.

1. **Triage Agent** validates severity, correlates duplicates, resolves ownership, and chooses the diagnostic path. It cannot call mutation tools.
2. **Context Aggregator** executes a pre-approved query plan against metrics, logs, traces, topology, runbooks, and change history. It returns normalized `Evidence` objects.
3. **Hypothesis Generator** proposes a small ranked set of falsifiable causes. Each hypothesis must identify supporting evidence, contradictory evidence, and the next discriminating query.
4. **Verifier Agent** independently checks claims and action preconditions using fresh data. It cannot rely on the generator’s prose as evidence.
5. **Remediation Planner** selects only registered actions, estimates blast radius, defines success criteria, and supplies a rollback plan.
6. **Policy and Approval Gate** is deterministic. It evaluates RBAC, environment, severity, confidence, action class, change freezes, and service-owner policy.
7. **Action Executor** invokes a signed, typed tool through the Tool Gateway. It has no general shell or arbitrary HTTP capability.
8. **Post-Action Verifier** measures recovery over an action-specific observation window. It closes, rolls back, or escalates the incident.
9. **Incident Scribe** writes an evidence-linked timeline and RCA draft without modifying operational state.

The workflow alternates reasoning and observation but has hard limits. A hypothesis that cannot be discriminated within the remaining budget is marked unresolved and handed to a human.

### 3.2 Action classification

| Class | Examples | Execution policy |
|---|---|---|
| D0: deterministic routing | dedupe, ownership lookup, severity mapping | Autonomous |
| D1: read-only query | metrics, logs, traces, topology, deploy history | Autonomous with scoped identity |
| D2: reversible low-risk change | clear approved cache, renew certificate through managed workflow | Autonomous only with explicit pre-authorization |
| D3: destructive or traffic-affecting | pod restart, traffic shift, rollback, scaling beyond bounds | Human-in-the-Loop approval required |
| D4: high-blast-radius or irreversible | database mutation, regional failover, data deletion | Prohibited for the AI system in the initial release |

A pod restart is treated as destructive even if Kubernetes recreates the pod: it can reduce capacity, erase volatile evidence, or amplify a cascading failure. Semantic labels do not determine risk; service policy and estimated blast radius do.

### 3.3 Human-in-the-Loop approval

For D3 actions, Slack or Teams presents a signed approval card containing:

- incident and service identity;
- proposed action with exact typed parameters;
- evidence-backed rationale and confidence;
- expected impact and maximum blast radius;
- preconditions, success criteria, observation window, and rollback;
- policy decision and approver role requirement;
- expiration time and a link to full evidence.

Approval is bound to the plan hash, action parameters, environment, and current incident version. Any plan mutation invalidates approval. Two-person approval is required for production traffic shifts above a configured threshold. Expired requests fail closed. Chat reactions alone are not authorization unless the collaboration platform maps them to a verified identity and a signed backend approval record.

### 3.4 Tool Gateway contract

Every tool is a versioned RPC with a JSON schema, service identity, timeout, retry policy, and side-effect classification. The gateway enforces:

- workload identity and least-privilege authorization;
- parameter validation and resource scoping;
- per-service concurrency and rate limits;
- idempotency keys for mutations;
- dry-run support where the target API permits it;
- immutable request and response audit events;
- egress allowlists and payload size limits;
- cancellation and circuit breaking.

Tools return structured observations with provenance. They never return an unbounded terminal transcript directly to the model.

### 3.5 Remediation transaction and verification

Distributed infrastructure cannot generally provide an atomic transaction across Kubernetes, traffic control, and deployment systems. The executor therefore uses a saga:

1. re-read preconditions immediately before execution;
2. acquire a scoped remediation lease to prevent competing actions;
3. execute one bounded step with an idempotency key;
4. observe golden signals over the defined window;
5. commit the step if postconditions hold;
6. otherwise execute the registered compensation action or stop and escalate.

A successful API response is not a successful remediation. Verification evaluates service-level indicators, error budget impact, and collateral regressions in dependent services. The system closes an incident only after stable health for the configured window.

## 4. Self-Optimization and Continuous Learning Loop

### 4.1 Feedback capture

The feedback system records both explicit and implicit signals.

**Explicit feedback** includes thumbs up or down, an operator-selected rejection reason, edited diagnosis, corrected root cause, approved or rejected action, and final incident review. Free-text corrections are useful but are never treated as ground truth without an identified reviewer and evidence.

**Implicit feedback** includes whether the recommendation was followed, whether the action succeeded, time to acknowledge, time to mitigate, reopen rate, escalation path, rollback occurrence, and whether later postmortem findings contradicted the initial diagnosis.

All feedback joins against immutable versions of the alert, prompt, model, retrieval index, evidence set, tool outputs, and policy. Without version lineage, an apparent model improvement cannot be attributed or reproduced.

### 4.2 Automated dataset curation

Raw operational data passes through a quarantine pipeline before entering any evaluation or training corpus:

1. **PII and secret redaction:** combine deterministic detectors for tokens, credentials, email addresses, customer identifiers, and IP policy with a contextual classifier. Replace values with stable typed placeholders when relationships must be retained.
2. **Access-policy projection:** preserve source ACLs in the knowledge index. Training export requires a separate approved data classification; retrieval permission does not imply training permission.
3. **Normalization:** canonicalize timestamps, service IDs, error signatures, and tool schemas while retaining the original incident reference.
4. **Deduplication:** use exact hashes plus semantic clustering to prevent an alert storm from dominating the dataset.
5. **Quality gates:** require a resolved status, evidence coverage, known outcome, and reviewer confidence. Exclude incidents with disputed RCAs or incomplete timelines.
6. **Contamination control:** split datasets by service and time, not random message, so near-duplicate incidents do not leak into evaluation.
7. **Adversarial filtering:** detect prompt injection in logs, tickets, and documents; mark external text as untrusted data and exclude instruction-like content from control channels.
8. **Retention and deletion:** attach lineage so privacy deletion or source expiration can remove derived embeddings and training examples.

### 4.3 Model adaptation with PEFT and DPO

Fine-tuning is not the first response to every failure. Prompt, tool, retrieval, and policy defects are corrected at their owning layer. Model adaptation is considered when a stable pattern remains across a sufficiently large, high-quality dataset.

Resolved incidents can produce:

- supervised examples for typed triage, evidence selection, and report generation;
- preference pairs where an operator-approved, evidence-grounded response is preferred over a rejected or ungrounded response;
- tool-selection trajectories stripped of secrets and unsupported actions.

Parameter-efficient fine-tuning with LoRA reduces release cost and isolates domain adapters. Direct Preference Optimization can improve ranking between safe and unsafe or grounded and ungrounded outputs without deploying an online reward loop. Human preference is not automatically correctness: preference examples must pass evidence and policy validation before DPO export.

Every adapter is versioned with its base model, tokenizer, data manifest, code revision, and safety evaluation. Promotion proceeds through offline evaluation, replay, shadow traffic, canary services, and rollback-capable production rollout. Online self-modification is prohibited.

### 4.4 RAG update and evaluation loop

The knowledge plane consumes CDC or scheduled exports from approved sources. Documents are parsed into semantically coherent sections, enriched with service ownership and validity intervals, embedded, and committed to a versioned index. Graph edges are built from Kubernetes manifests, service mesh traffic, CMDB relations, and deployment metadata. Index publication is atomic: readers use either the previous complete version or the next complete version.

RAG quality is evaluated on the **RAG Triad**:

- **Context relevance:** did retrieval return evidence needed for the incident and avoid irrelevant context?
- **Groundedness:** is each generated claim entailed by cited evidence?
- **Answer relevance:** does the report answer the operational question and propose a discriminating next step?

These model-based metrics are supplemented with deterministic measures: recall of known causal evidence, citation validity, stale-document rate, retrieval latency, ACL leakage tests, no-answer accuracy, and downstream remediation success. LLM-as-judge scores are calibrated against SRE labels and never serve as the sole release gate.

A CI pipeline replays a frozen incident set whenever chunking, embeddings, reranking, prompts, graph construction, or models change. Releases fail when they regress critical slices such as major incidents, sparse telemetry, multilingual logs, or malicious document content.

## 5. Production Guardrails, Security, and Reliability

### 5.1 Claim verification and hallucination prevention

Every material claim in an RCA is represented internally as `{claim, citation_ids, entailment_status}`. The Verifier checks that citations exist, were authorized for the incident principal, fall within the relevant time window, and support the claim. Unsupported claims are removed or explicitly labeled as hypotheses.

The report distinguishes three epistemic states:

- **Observed:** directly supported by telemetry or an authoritative record;
- **Inferred:** consistent with cited evidence but not yet proven;
- **Unknown:** evidence is missing or contradictory.

Retrieved logs and documents are untrusted input. They are wrapped as data, stripped of executable markup, and never allowed to override system policy. Prompt-injection tests are part of every retrieval release.

### 5.2 Budget and loop controls

Each incident receives a budget envelope based on severity and tenant policy:

| Control | Example default |
|---|---:|
| End-to-end diagnostic deadline | 30 seconds |
| Maximum agent transitions | 12 |
| Maximum tool calls | 20 |
| Maximum calls to one backend | 6 |
| Maximum retrieved context | 32,000 tokens |
| Maximum generated tokens | 4,000 tokens |
| Maximum concurrent incidents per service | 2 |
| Maximum autonomous mutations per incident | 1 |

The orchestrator tracks tokens, wall-clock time, tool cost, and repeated call signatures. Repeated equivalent queries trigger loop detection. Provider and backend rate limits use token buckets keyed by tenant, service, and incident. When a budget is exhausted, the system emits its evidence, unresolved questions, and recommended human next step instead of attempting an unbounded continuation.

### 5.3 Identity, RBAC, and data isolation

The system uses short-lived workload identities. Each tool call is authorized against the incident’s service scope, environment, action class, and caller role. The model never receives cloud credentials. Production and non-production tool gateways use separate identities and network boundaries.

Knowledge retrieval is security-trimmed before ranking. A vector similarity match cannot bypass source ACLs. Cross-tenant and cross-business-unit indexes are physically or cryptographically isolated where required. Audit records include the human approver, policy bundle hash, model and prompt versions, evidence IDs, and exact action parameters.

Telemetry passes through PII redaction before model access. Redaction occurs as close to ingestion as possible, with a second egress scan before provider calls. Highly sensitive services can require an approved in-region or self-hosted model and can disable raw-log retrieval entirely.

### 5.4 Reliability patterns

- **Bulkheads:** isolate queues and worker pools by tenant and severity so an alert storm cannot starve critical incidents.
- **Circuit breakers:** stop calls to degraded model, search, and observability providers; expose partial availability explicitly.
- **Backpressure:** group duplicate alerts and cap context refresh frequency.
- **Idempotency:** require stable incident, workflow, and action keys.
- **Leases:** prevent simultaneous remediations against the same resource.
- **Fail-closed policy:** inability to evaluate policy or authorization prohibits mutation.
- **Fallback:** produce a deterministic incident packet and page the human owner when inference is unavailable.
- **Disaster recovery:** replicate the incident ledger and workflow state across failure domains; test regional recovery and queue replay.

The system itself has SLOs and synthetic canaries. A dedicated kill switch disables all mutation tools without disabling alert ingestion or evidence collection. Service owners also receive per-service automation switches.

### 5.5 Rollout plan

1. **Offline replay:** evaluate historical incidents with no live access.
2. **Shadow mode:** process live alerts but expose results only to evaluators.
3. **Advisory mode:** show diagnosis and plans to on-call engineers; all actions are manual.
4. **Approved execution:** execute D2 and D3 actions only after explicit approval.
5. **Limited autonomy:** enable one D2 runbook at a time for canary services with small blast radius.
6. **Scaled autonomy:** expand only after meeting safety, precision, MTTR, and reopen-rate gates for at least one full on-call rotation.

Any unsafe proposal, ACL leak, unexplained action, or statistically significant regression returns the affected automation class to advisory mode.

## 6. Technical Implementation Specification

### 6.1 Pydantic event and RCA schemas

The following Pydantic v2 models define the stable boundary between alert ingestion, orchestration, and downstream incident systems. Production deployments should generate JSON Schema from these types and version it in a schema registry.

```python
from __future__ import annotations

from datetime import datetime
from enum import Enum
from typing import Annotated, Literal
from uuid import UUID

from pydantic import BaseModel, ConfigDict, Field, HttpUrl


class StrictModel(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)


class Severity(str, Enum):
    SEV1 = "SEV1"
    SEV2 = "SEV2"
    SEV3 = "SEV3"
    SEV4 = "SEV4"


class Environment(str, Enum):
    PRODUCTION = "production"
    STAGING = "staging"
    DEVELOPMENT = "development"


class ServiceRef(StrictModel):
    service_id: str = Field(min_length=1, max_length=128)
    owner_team: str = Field(min_length=1, max_length=128)
    environment: Environment
    region: str | None = Field(default=None, max_length=64)
    cluster: str | None = Field(default=None, max_length=128)
    namespace: str | None = Field(default=None, max_length=128)


class AlertEvent(StrictModel):
    schema_version: Literal["1.0"] = "1.0"
    event_id: UUID
    source: Literal["pagerduty", "alertmanager", "cloudwatch", "datadog"]
    source_event_id: str = Field(min_length=1, max_length=256)
    fingerprint: str = Field(min_length=16, max_length=256)
    received_at: datetime
    started_at: datetime
    severity: Severity
    alert_name: str = Field(min_length=1, max_length=256)
    summary: str = Field(min_length=1, max_length=2_000)
    service: ServiceRef
    labels: dict[str, str] = Field(default_factory=dict)
    annotations: dict[str, str] = Field(default_factory=dict)
    generator_url: HttpUrl | None = None
    runbook_url: HttpUrl | None = None
    correlation_keys: list[str] = Field(default_factory=list, max_length=32)


class Evidence(StrictModel):
    evidence_id: str = Field(pattern=r"^[a-z]+:[A-Za-z0-9._:/-]+$")
    source_type: Literal["metric", "log", "trace", "runbook", "topology", "git", "deployment"]
    source_uri: str
    observed_at: datetime
    retrieved_at: datetime
    excerpt: str = Field(max_length=4_000)
    query_hash: str | None = None
    redaction_applied: bool = False


class Claim(StrictModel):
    statement: str = Field(min_length=1, max_length=2_000)
    status: Literal["observed", "inferred", "unknown"]
    citation_ids: list[str] = Field(default_factory=list)
    verification: Literal["supported", "contradicted", "insufficient"]


class ProposedAction(StrictModel):
    action_id: UUID
    tool_name: str
    tool_version: str
    action_class: Literal["D0", "D1", "D2", "D3", "D4"]
    parameters: dict[str, str | int | float | bool]
    rationale_claim_ids: list[int]
    expected_impact: str
    max_blast_radius: str
    success_criteria: list[str]
    rollback_tool: str | None = None
    approval_required: bool
    approval_state: Literal["not_required", "pending", "approved", "rejected", "expired"]


class RCAReport(StrictModel):
    schema_version: Literal["1.0"] = "1.0"
    incident_id: UUID
    alert_event_id: UUID
    created_at: datetime
    engine: Literal["direct_prompt", "rag", "human_fallback"]
    status: Literal["diagnosed", "mitigated", "resolved", "escalated", "inconclusive"]
    confidence: Annotated[float, Field(ge=0.0, le=1.0)]
    executive_summary: str = Field(max_length=4_000)
    root_cause: str | None = Field(default=None, max_length=4_000)
    claims: list[Claim]
    evidence: list[Evidence]
    proposed_actions: list[ProposedAction] = Field(default_factory=list)
    verification_summary: str | None = Field(default=None, max_length=4_000)
    unresolved_questions: list[str] = Field(default_factory=list)
    escalation_reason: str | None = None
    model_version: str
    prompt_version: str
    retrieval_index_version: str | None = None
    policy_bundle_version: str
    total_tool_calls: int = Field(ge=0)
    input_tokens: int = Field(ge=0)
    output_tokens: int = Field(ge=0)
```

Additional cross-field validation should enforce that observed claims have citations, D3 actions require approval, D4 actions cannot be executable, and a `resolved` report includes successful post-action verification.

### 6.2 Engine Router pseudocode

This example uses LangChain-style structured output while keeping authorization and routing outside the model. It is intentionally pseudocode: provider, workflow, and policy adapters are deployment-specific.

```python
from dataclasses import dataclass
from datetime import UTC, datetime
from typing import Protocol

from langchain_core.language_models import BaseChatModel
from langchain_core.prompts import ChatPromptTemplate


@dataclass(frozen=True)
class RouteDecision:
    mode: str
    reason_codes: tuple[str, ...]
    registry_rule_id: str | None


class PolicyEngine(Protocol):
    async def evaluate_quick_path(self, alert: AlertEvent, rule: object) -> object: ...
    async def authorize_plan(self, alert: AlertEvent, plan: object) -> object: ...


class AutomationRegistry(Protocol):
    async def exact_match(self, alert: AlertEvent) -> object | None: ...


class EngineRouter:
    def __init__(
        self,
        registry: AutomationRegistry,
        policy: PolicyEngine,
        quick_llm: BaseChatModel,
        rag_engine: "RAGDiagnosticEngine",
        workflow: "DurableWorkflowClient",
    ) -> None:
        self.registry = registry
        self.policy = policy
        self.quick_llm = quick_llm
        self.rag_engine = rag_engine
        self.workflow = workflow

    async def route(self, alert: AlertEvent) -> RouteDecision:
        rule = await self.registry.exact_match(alert)
        if rule is None:
            return RouteDecision("rag", ("NO_REGISTRY_MATCH",), None)

        check = await self.policy.evaluate_quick_path(alert, rule)
        if not check.allowed:
            return RouteDecision("rag", tuple(check.reason_codes), rule.id)

        return RouteDecision("direct_prompt", ("ALL_QUICK_PATH_GATES_PASSED",), rule.id)

    async def diagnose(self, alert: AlertEvent) -> RCAReport:
        decision = await self.route(alert)

        if decision.mode == "direct_prompt":
            try:
                report = await self._run_quick_path(alert, decision.registry_rule_id)
            except (TimeoutError, SchemaValidationError, PreconditionsChanged):
                # Quick path fails over to richer diagnosis, never to broader permissions.
                report = await self.rag_engine.diagnose(alert, reason="QUICK_PATH_FAILED")
        else:
            report = await self.rag_engine.diagnose(
                alert,
                reason=",".join(decision.reason_codes),
            )

        # Persist before any approval or action. The workflow owns retries and idempotency.
        await self.workflow.record_report(report)
        return report

    async def _run_quick_path(self, alert: AlertEvent, rule_id: str) -> RCAReport:
        rule = await self.registry.get_versioned(rule_id)
        live_facts = await rule.read_only_preflight(alert, timeout_seconds=2)

        prompt = ChatPromptTemplate.from_messages([
            ("system", QUICK_PATH_SYSTEM_PROMPT_V7),
            ("human", "Alert: {alert_json}\nRule: {rule_json}\nFacts: {facts_json}"),
        ])
        chain = prompt | self.quick_llm.with_structured_output(RCAReport, strict=True)
        report = await chain.ainvoke({
            "alert_json": alert.model_dump_json(),
            "rule_json": rule.safe_prompt_view(),
            "facts_json": live_facts.model_dump_json(),
        })

        assert report.engine == "direct_prompt"
        assert report.total_tool_calls <= rule.max_tool_calls
        assert all(a.tool_name in rule.allowed_tools for a in report.proposed_actions)

        verification = verify_all_claims(report.claims, live_facts.evidence)
        if not verification.all_supported:
            raise PreconditionsChanged("quick-path claims were not verified")

        authorization = await self.policy.authorize_plan(alert, report.proposed_actions)
        if not authorization.allowed:
            return report.model_copy(update={
                "status": "escalated",
                "escalation_reason": authorization.reason,
                "proposed_actions": [],
            })
        return report
```

The RAG engine follows the same typed boundary but constructs context through parallel, deadline-aware retrievers:

```python
class RAGDiagnosticEngine:
    async def diagnose(self, alert: AlertEvent, reason: str) -> RCAReport:
        entities = await self.entity_resolver.resolve(alert.service)
        evidence = await gather_with_deadline(
            timeout_seconds=18,
            tasks=[
                self.telemetry.retrieve(alert, entities),
                self.graph.topological_retrieve(alert, entities, max_hops=2),
                self.runbooks.hybrid_retrieve(alert, entities, acl=alert.service),
                self.changes.retrieve(alert, entities),
            ],
        )
        ranked = self.reranker.rank_and_budget(evidence, max_tokens=32_000)
        hypotheses = await self.hypothesis_agent.generate(alert, ranked, limit=3)
        tested = await self.query_planner.discriminate(
            hypotheses,
            remaining_tool_calls=8,
            deadline_seconds=8,
        )
        draft = await self.rca_agent.create_structured_report(alert, ranked, tested)
        return await self.claim_verifier.verify_or_downgrade(draft)
```

### 6.3 Operational metrics

The platform exports metrics by route, alert class, service, model, prompt, retrieval index, and policy version:

- routing rate and router disagreement rate;
- diagnosis latency and time spent per dependency;
- tool-call count, error rate, retry rate, and loop aborts;
- token and monetary cost per incident;
- evidence recall, citation coverage, and verifier rejection rate;
- recommendation acceptance, remediation success, rollback, and reopen rate;
- autonomous resolution rate and false-closure rate;
- approval latency and rejection reasons;
- ACL denial and redaction counts;
- MTTA and MTTR compared with matched historical baselines.

Dashboards must separate “automation attempted,” “diagnosis accepted,” “action executed,” and “incident resolved.” Combining them into one automation metric hides unsafe failures.

### 6.4 Key design decisions

1. **Workflow state is authoritative; chat is an interface.** Slack or Teams may disappear without losing approvals, evidence, or incident progress.
2. **Policies authorize actions, not models.** Confidence influences escalation but cannot grant capability.
3. **Retrieval indexes are versioned derived data.** Authoritative documents, telemetry, and topology remain the source of truth.
4. **Autonomy is earned per alert class and runbook.** There is no global “autonomous agent” switch.
5. **Verification is part of remediation.** An action without observed recovery is incomplete.
6. **Learning is offline and gated.** Production outcomes improve future releases but never rewrite the live model or policy directly.

This architecture can remove repetitive operational work while preserving the properties expected of production infrastructure: bounded behavior, least privilege, durable execution, evidence-based decisions, measurable reliability, and a clear human override at every high-risk boundary.
